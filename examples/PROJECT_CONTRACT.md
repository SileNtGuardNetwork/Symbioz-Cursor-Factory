## Task contract

### Target

What observable result must exist after the task?

### Scope

Which files, packages, routes, schemas, integrations, or documents may change?

### Verification

Which commands, tests, browser flows, screenshots, logs, or preview links prove completion?

### Stop condition

What useful adjacent work is explicitly out of scope?

### Approval boundary

Which actions require owner approval?

Typical approval boundaries:

- adding dependencies
- changing architecture
- changing database schema
- applying migrations
- connecting new external services
- changing billing
- exposing customer data
- creating paid resources
- deploying to production
- publishing public content

## Quality gates

- [ ] Relevant tests pass
- [ ] Type checking passes
- [ ] Lint passes
- [ ] Production build passes
- [ ] Browser flow is verified when UI or routes changed
- [ ] No secrets or private data were added
- [ ] Documentation reflects changed behavior
- [ ] Evidence is attached

## Known constraints

List legal, security, budget, platform, performance, accessibility, or timeline constraints.

## Definition of done

The task is done only when the target exists, verification passes, evidence is available, scope stayed bounded, and required approvals were obtained.
